Introduction & Business Outcomes

The syllabus is the basis for the Foundation Level exam and serves member boards, certification bodies, training providers, and candidates. It's aimed at anyone touching software testing — testers, analysts, developers, product owners, and managers — and is the entry point to ISTQB's Core Advanced, Expert, Agile, and Specialist certification tracks.

1.1 · What is Testing?

Testing is a set of activities to discover defects and evaluate quality of work products (test objects). It's more than execution — it includes planning, analysis, design, implementation, and completion. Testing covers both verification ("did we build it to spec?") and validation ("did we build the right thing for the user?"). It can be dynamic (executing software) or static (no execution — reviews, static analysis).

Typical objectives: evaluate work products, cause failures & find defects, ensure coverage, reduce risk of poor quality, verify requirements/compliance, inform stakeholder decisions, build confidence, and validate the object meets stakeholder expectations.

Testing vs. debugging

Testing finds/triggers defects; debugging (a development activity) reproduces, diagnoses, and fixes them. After a fix: confirmation testing checks the original defect is gone; regression testing checks nothing else broke.

1.2 · Why is Testing Necessary?

  • Cost-effective defect detection → indirectly raises quality (defects are removed via debugging)
  • Direct quality evaluation feeding release decisions across the SDLC
  • Gives users indirect representation in the project
  • May be mandated by contracts, law, or regulation

Testing vs. Quality Assurance

Testing is product-oriented & corrective (a form of quality control). QA is process-oriented & preventive — good process ⇒ good product — and is everyone's responsibility.

Errors → Defects → Failures

Human errors (mistakes) create defects (bugs); an executed defect may cause a failure. Not all defects fail every time; failures can also come from environmental conditions. Root cause analysis targets the underlying reason to prevent recurrence.

1.3 · The Seven Testing Principles

  1. Testing shows presence, not absence, of defects. It reduces undiscovered defects but can't prove correctness.
  2. Exhaustive testing is impossible. Use techniques, prioritization, and risk to focus effort.
  3. Early testing saves time and money. Start static and dynamic testing as early as possible.
  4. Defects cluster together (Pareto principle) — predicted/observed clusters drive risk-based testing.
  5. Tests wear out. Repeated tests lose power to find new defects; vary and refresh them.
  6. Testing is context dependent. No universal approach fits every project.
  7. Absence-of-defects is a fallacy. A bug-free system can still fail to meet real user needs — validation matters too.

Context factors shaping the process: stakeholders, team skills, business domain, technical factors, project constraints, org factors, SDLC model, and tooling.

Traceability links test basis ↔ testware ↔ results ↔ defects — it drives coverage evaluation, impact analysis, audits, and clearer reporting.

Two principal roles: test management (planning, monitoring, control, completion) and testing (analysis, design, implementation, execution) — one person can hold both.

1.5 · Essential Skills & Good Practices

Generic skills

  • Testing & domain knowledge
  • Thoroughness, curiosity, attention to detail
  • Communication & active listening
  • Analytical/critical thinking, creativity
  • Technical knowledge

Independence of testing

  • None → author tests own work
  • Some → peer from same team
  • High → tester outside the team
  • Very high → tester outside the org
  • Benefit: fresh perspective; risk: isolation from dev team

The whole team approach (from Extreme Programming) has any skilled member perform any task, with shared responsibility for quality — great for collaboration, but not always appropriate (e.g., safety-critical systems may need higher independence).

2.1 · SDLC Context

SDLC models: sequential (waterfall, V-model), iterative (spiral, prototyping), incremental (Unified Process) — plus finer-grained methods like ATDD, BDD, DDD, XP, FDD, Kanban, Lean IT, Scrum, TDD. The chosen model impacts test scope/timing, documentation detail, technique choice, automation extent, and tester responsibilities.

Test-first approaches

  • TDD — write test, then code, then refactor
  • ATDD — derive tests from acceptance criteria before building
  • BDD — Given/When/Then natural-language behavior specs

DevOps & testing

  • Fast feedback via CI/CD pipelines
  • Promotes shift left; stable, automated environments
  • Risk: pipeline/tooling upkeep, automation resourcing

Shift left = perform testing earlier (review specs, write tests before code, static analysis before dynamic, non-functional testing from component level) — without neglecting later-stage testing. Retrospectives (what worked / what didn't / how to improve) drive continuous improvement and feed the test completion report.

2.2 · Test Levels & Test Types

LevelFocus

Component integration testingInterfaces/interactions between components

System integration testingInterfaces between the system and external systems/services
Acceptance testingValidation & deployment readiness — UAT, operational, contractual, regulatory, alpha/beta

Confirmation testing re-checks that a specific defect is fixed. Regression testing checks that a change hasn't broken anything else — a prime automation candidate, especially under CI.

2.3 · Maintenance Testing

Triggered by modifications (planned enhancements, corrective fixes, hot fixes), upgrades/migrations of the operational environment, or retirement of a system (data archiving/restore testing). Scope depends on change risk, system size, and change size.

3.1 · Static Testing Basics

Static testing examines work products without executing code — via manual review or tool-based static analysis. It can be applied almost anywhere: requirements, code, test plans, contracts, models. It catches defects dynamic testing can't (unreachable code, requirement ambiguity) and catches them earlier and cheaper — especially requirement/design defects, coding-standard deviations, interface mismatches, and certain security flaws.

Static testingDynamic testing
Finds defects directlyCauses failures → defect found via analysis
Works on non-executable productsRequires executable code
Measures e.g. maintainabilityMeasures e.g. performance efficiency
Reaches rarely-executed code paths easilyCan struggle to reach them

3.2 · Feedback & Review Process

Early, frequent stakeholder feedback prevents costly rework and missed deadlines by catching misunderstandings before they compound.

  1. Planning — define scope, criteria, effort, timeframe
  2. Review initiation — distribute materials, confirm roles
  3. Individual review — each reviewer logs anomalies solo
  4. Communication & analysis — discuss, triage, agree follow-ups
  5. Fixing & reporting — log defects, confirm exit criteria, report results

Review roles

  • Manager — resources, scope decision
  • Author — creates/fixes the product
  • Moderator — runs the meeting
  • Scribe — records anomalies/decisions
  • Reviewer — performs the review
  • Review leader — overall responsibility

Review types (least → most formal)

  • Informal — no defined process
  • Walkthrough — led by author
  • Technical review — led by moderator, technical peers
  • Inspection — most formal, metrics-driven; author can't be leader/scribe

Success factors: clear objectives/exit criteria, right review type for context, small review chunks, feedback loop to authors, prep time, management support, cultural buy-in, training, and good facilitation.

4.1 · Technique Families

Black-box

Specification-based; independent of implementation, so test cases survive refactors.

White-box

Structure-based; depends on code/design, so it can only be built after implementation.

Experience-based techniques lean on tester skill/knowledge, complementing the two structured families.

4.2 · Black-Box Techniques

TechniqueIdea100% coverage means…
Equivalence PartitioningGroup data expected to be handled the same wayEvery partition (valid & invalid) hit ≥1×
Boundary Value AnalysisBugs cluster at partition edges2-value: boundary + nearest neighbor; 3-value: boundary + both neighbors
Decision Table TestingMap condition combinations → actionsEvery feasible rule/column exercised
State Transition TestingModel states, events, transitionsAll states / all valid transitions / all transitions (incl. invalid)

4.3 · White-Box Techniques

  • Statement testing — coverage item = executable statement; 100% ⇒ every line executed at least once
  • Branch testing — coverage item = branch (true/false, switch outcomes, loop exit); subsumes statement coverage

White-box testing reveals defects even when specs are vague or outdated — but can't detect missing functionality (defects of omission).

4.4 · Experience-Based Techniques

Error guessing

Anticipate likely defects from past behavior, common developer mistakes, and similar-app failure history (a.k.a. fault attacks).

Exploratory testing

Simultaneous design/execution/evaluation; often session-based, guided by a test charter, ending in a debrief.

Checklist-based testing executes tests against a maintained checklist — flexible, but less repeatable than scripted test cases.

4.5 · Collaboration-Based Approaches

User stories follow the 3 C's: Card, Conversation, Confirmation. Good stories are INVEST: Independent, Negotiable, Valuable, Estimable, Small, Testable. Acceptance criteria are usually written scenario-oriented (Given/When/Then) or rule-oriented (bullet/tabular).

ATDD: a specification workshop defines/refines the story and criteria → test cases are derived (positive first, then negative, then non-functional) → developers automate them as executable requirements.

5.1 · Test Planning

A test plan documents objectives, schedule, and approach, and demonstrates alignment with test policy/strategy. Typical content: context, assumptions/constraints, stakeholders, communication plan, risk register, test approach, budget/schedule.

Entry vs. exit criteria

Entry = preconditions to start (resources, testware, initial quality). Exit = what "done" means (coverage achieved, defect thresholds, tests executed). Running out of time/budget can itself be an accepted exit criterion.

Estimation techniques

  • Ratio-based (e.g., dev:test = 3:2)
  • Extrapolation from early iteration data
  • Wideband Delphi / Planning Poker
  • Three-point: E = (a + 4m + b) / 6

Test case prioritization: risk-based, coverage-based, or requirements-based — constrained by dependencies and resource availability.

Test pyramid

Bottom layer = many small, fast, isolated tests (unit); top layer = fewer, slower, high-level end-to-end tests. Higher layer ⇒ lower isolation, higher execution time.

Testing quadrants (Marick)

  • Q1 — technology-facing, supports team (component tests, automated in CI)
  • Q2 — business-facing, supports team (functional/acceptance tests)
  • Q3 — business-facing, critiques product (exploratory, usability, UAT — often manual)
  • Q4 — technology-facing, critiques product (non-functional, smoke — often automated)

5.2 · Risk Management

Risk = likelihood × impact. Project risks threaten schedule/budget/scope (organizational, people, technical, supplier issues). Product risks threaten quality characteristics (missing functionality, security holes, poor performance) with consequences ranging from user dissatisfaction to, in extreme cases, physical harm.

Product risk analysis (identification + assessment) shapes test scope, levels, techniques, coverage targets, effort, and prioritization. Risk control (mitigation + monitoring) response options: mitigate via testing, accept, transfer, or contingency-plan.

5.3 · Monitoring, Control & Completion

Metric familyExamples
Project progressTask completion, resource usage, effort
Test progressCases run/passed/failed, execution time
Product qualityAvailability, response time, MTTF
DefectCount/priority, density, detection %
CoverageRequirements, code coverage

Test progress reports (frequent, informal) support ongoing control; test completion reports (formal, one-off) summarize a finished activity — both may use dashboards, chat, or formal documents depending on audience and team distribution.

5.4 · Configuration Management

CM uniquely identifies, version-controls, and tracks testware as configuration items, turning them into baselines changeable only via formal change control — enabling reproducible test results, often automated inside a DevOps pipeline.

5.5 · Defect Management

A defect report typically includes: unique ID, title/summary, date/author/role, test object & environment, context, reproduction steps, expected vs. actual results, severity, priority, status, and references.

6.1 · Tool Categories

Test management · static testing (reviews/analysis) · test design & implementation · execution & coverage · non-functional testing · DevOps/CI-CD · collaboration · scalability/containerization — plus anything else pressed into service (even a spreadsheet counts).

6.2 · Automation — Benefits vs. Risks

Benefits

  • Saves time on repetitive manual work
  • More consistent, repeatable execution
  • Objective measures too complex for manual tracking
  • Easier progress/quality reporting
  • Faster feedback → earlier defect detection
  • Frees testers for deeper, exploratory work

Risks

  • Unrealistic expectations of tool capability
  • Underestimated introduction/maintenance cost
  • Over-reliance, displacing human critical thinking
  • Vendor/open-source dependency & abandonment
  • Platform incompatibility
  • Regulatory/safety non-compliance
